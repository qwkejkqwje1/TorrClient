# Как устроен TorrClient

Полное описание проекта: что входит в сборку, как части связаны между собой, какие
данные где лежат и что происходит при запуске. Описание описывает код по состоянию
на 27.09.2026.

---

## 1. Что это такое

TorrClient — портативная (без установки) программа для работы с раздачами на
своём домашнем сервере. Взяв файл `.torrent` или магнит-ссылку, вы добавляете
раздачу на свой сервер, а программа помогает её найти, показать метаданные,
продолжить просмотр с места остановки и следить за новыми сериями по подписке.

Три главных свойства, которые определили всю конструкцию:

- **Портативность.** Ничего не ставится в систему. Папку можно скопировать на
  флешку и запустить на другой машине. Отсюда — свои пути хранения, никаких
  внешних сервисов и никаких зависимостей, которые нельзя положить рядом.
- **Свой сервер — единственный источник истины.** Раздачи живут на TorrServer
  (движок), а программа — интерфейс к нему плюс удобства поверх.
- **Данные не должны теряться.** Отметки просмотра, избранное и подписки
  накапливаются месяцами и ничем не восстанавливаются. Из-за этого состояние
  пишется атомарно, с номером формата, и попадает в бэкап.

## 2. Состав: три программы

Проект собирается в три независимые части. Каждая может работать сама по себе,
но рассчитана на совместную работу.

| Часть | Что это | Где исходники | Порт |
| --- | --- | --- | --- |
| **Оболочка** (Wails) | Окно программы, трей, запуск и надзор за остальными | `app/` | — |
| **Демон** | HTTP-сервер: API, живая лента, сторожа, файл состояния | корень репозитория | **8099** |
| **TorrServer** | Движок раздач (сторонний, прикладывается рядом) | — | **8090** |

Ключевое: **демон не знает про оболочку**, а оболочка не знает про логику
демона. Связь только через HTTP и файл состояния. Благодаря этому демон
запускается и без окна (например, для добавления магнита из командной строки), а
оболочку можно заменить браузером.

### 2.1 Оболочка (`app/`)

Окно на Go + Wails (WebView2), в котором показан веб-интерфейс. Оболочка
выполняет четыре задачи и ничего больше:

1. **Поднимает TorrServer**, если тот не отвечает. Ищет движок рядом с собой
   (`findUp`), поднимает и запоминает, что подняла сама — чтобы потом не
   считать своим чужой процесс, который пользователь запустил вручную.
2. **Поднимает демон** и ждёт его готовности.
3. **Следит за живостью обоих** (`healthLoop`) и перезапускает упавшее. У TorrServer
   есть `tsStartGrace` — нескольких минут терпения после запуска, чтобы
   перезапуском не прерывался его штатный старт.
4. **Показывает иконку в трее**, сворачивание окна вместо выхода, меню
   «Открыть / Выход».

Готовность проверяется **ответом `/echo`**, а не открытым портом. Это принципиально:
сервер открывает сокет раньше, чем начнёт отвечать, и запрос в этот промежуток
рвётся — снаружи это выглядит как «поиск молчит» при живом процессе. Ожидание
прекращается по двум независимым условиям: сервер ответил либо процесс умер.
Срок задаётся **временем** (`tsReadyWait` 12 с, `daemonReadyWait` 15 с), а не
числом попыток: одна проба может занять сама по себе `healthTimeout`, и счёт
попыток превращал бы «12 секунд» в минуту с лишним.

Трей написан своей Win32-реализацией (`app/tray.go`), без стороннего модуля:
портативная сборка обязана собираться из того, что лежит рядом. Используются
`Shell_NotifyIconW` и невидимое окно-получатель сообщений на `HWND_MESSAGE`.
Иконка берётся из `app.ico` рядом с программой, при отсутствии — стандартная
системная; ошибка не фатальна, без иконки закрытие окна снова означает выход.

### 2.2 Демон (корень репозитория)

HTTP-сервер на loopback. Он и есть «настоящая» программа: оболочка лишь
показывает его интерфейс. Демон:

- отдаёт веб-интерфейс и API;
- держит живую ленту событий (SSE) для интерфейса;
- спрашивает TorrServer, трекеры и TMDB;
- ведёт сторожи раздач, подписок, закачек, отметок просмотра и кэша метаданных;
- хранит состояние пользователя.

Ключи запуска:

| Ключ | По умолчанию | Назначение |
| --- | --- | --- |
| `-port` | `8099` | порт демона |
| `-host` | `127.0.0.1` | адрес привязки |
| `-open` | `true` | открыть браузер при старте |
| `-magnet` | — | добавить магнит на активный сервер и выйти |
| `-torrent` | — | добавить `.torrent` и выйти |
| `-quiet` | `false` | не писать в консоль |

С `-magnet` или `-torrent` демон выполняет одну операцию и выходит, не поднимая
службу. Это то, что делает кнопка в проводнике Windows: «открыть с помощью».

**Важно про безопасность.** Вне loopback API открывается **без пароля**: профили
(включая пароли к серверу), позиции просмотра и управление раздачами доступны
любому, кто достал до адреса. Демон предупреждает об этом в журнал при запуске с
`-host`, отличным от loopback. Защита от браузерных атак другая и работает всегда
(раздел 5).

Версия собирается подстановкой: `-ldflags "-X main.version=..."`, значение по
умолчанию — `TorrClient 1.1-dev (MatriX/1.1.x)`.

### 2.3 Веб-интерфейс (`web/`)

Три файла, без сборки и без зависимостей: `index.html`, `app.js` (4448 строк,
256 КБ), `style.css` (355 строк). Обычный ES2020, без модулей и без фреймворков —
чтобы портативная сборка оставалась самодостаточной.

Десять страниц, выбор — одна таблица (в `app.js:325`):

| Страница | Назначение |
| --- | --- |
| `library` | Библиотека: раздачи с фильтрами и подборками |
| `search` | Поиск по трекерам |
| `favorites` | Избранное |
| `bookmarks` | Закладки на файлы |
| `players` | Обнаруженные плееры, проверка связи |
| `downloads` | Загрузки |
| `series` | Сериалы |
| `subs` | Подписки на сериалы |
| `settings` | Настройки |
| `server` | Состояние сервера |

## 3. Как запускается

Порядок в `main.go` выбран так, чтобы первый запрос интерфейса не увидел пустоту.

```
1. Разбор ключей, предупреждение о не-loopback адресе
2. Загрузка настроек → applyStoragePaths → setCfg
3. Чтение состояния ДО запуска службы:
      loadUserDataStore()   избранное, закладки, подборки
      loadSubs()            подписки
      viewedMarks.load()    отметки просмотра
      loadTmdbCache()       постеры и оценки
4. Если задан -magnet/-torrent → одна операция и выход
5. Создание Comp, запуск менеджера закачек
6. Запуск сторожей (каждый в своей горутине):
      dl.janitor()        уборка завершённых закачек старше суток
      torrentsWatcher()   слежение за раздачами на сервере
      subsWatcher()       проверка подписок на новые серии
      tmdbSaver()         отложенная запись кэша метаданных
      viewedJanitor()     уборка старых отметок просмотра
7. Сборка мукса, 28 маршрутов
8. Прослушивание порта, печать адресов в журнал
```

Пункт 3 принципиален: подписки, избранное и отметки просмотра читаются **до**
поднятия службы. Иначе первый же запрос интерфейса получил бы пустой список и
записал его на диск — то есть стёр бы накопленное.

Сторож запускаются раньше HTTP-сервера намеренно: они сразу переходят в спящий
режим и ждут своего первого тика, поэтому на скорость старта не влияют.

Со стороны оболочки (`app/app.go:104`):

```
startup
  ├── go startTorrServer()   поднять или дождаться движка
  ├── go startDaemon()       поднять демон
  ├── go healthLoop()        следить за обоими
  └── go setupTray()         иконка в лотке

OnBeforeClose → свернуть в трей (возврат true отменяет закрытие)
OnShutdown    → tray.stop(), остановка процесса демона
```

Подъём TorrServer и демона идёт **параллельно**: они не зависят друг от друга,
а последовательный запуск складывал их ожидания (до ~27 секунд при проблемах).

## 4. Данные и файлы

### 4.1 Где что лежит

| Файл | Папка | Что хранит | Версия формата | Права |
| --- | --- | --- | --- | --- |
| `torrclient.json` | рядом с программой | настройки, профили, плееры, ключ TMDB | нет | `0600` |
| `viewed.json` | `DataFolder` | отметки просмотра по раздачам и файлам | да | `0600` |
| `userdata.json` | `DataFolder` | избранное, закладки, подборки | да | `0600` |
| `subscriptions.json` | `DataFolder` | подписки на сериалы | да | `0600` |
| `tmdb-cache.json` | `CacheFolder` | постеры, оценки, сезоны | нет | `0600` |
| `torrclient.log` | `CacheFolder` | журнал, с ротацией | — | `0600` |

`CacheFolder` и `DataFolder` разведены намеренно: кэш можно удалить в любой
момент, а постоянные данные — нельзя.

**Про умолчания важно не ошибиться.** Пустая настройка означает «рядом с программой»
(`storageDir`, `config.go:189`), а не «на локальный диск»: так ведёт себя
портативная сборка и так же ведут себя уже настроенные копии, в файле которых
этих полей ещё нет. Снимка конфига может не быть вовсе — журнал пишется с первых
строк запуска, до чтения конфига, и падать на этом он не должен. Папки создаются
сами (`applyStoragePaths`), права `0755`.

Живая конфигурация этой машины лежит на диске `Y:` и держит `cache_folder` и
`data_folder` в одной папке — так тоже работает, но означает, что очистка кэша
снесёт и постоянные данные.

### 4.2 Версия формата состояния

Файлы с пометкой «версия формата» пишутся как

```json
{
  "version": 1,
  "data": { ...собственно данные... }
}
```

Смысл в том, что читать их должна вторая копия программы, а формат меняется.
Правила:

- **Файла без номера не бывает** — он всегда пишется с версией. Отсутствие
  номера означает прежнюю сборку, и такой файл читается как был. Иначе поломка
  затронула бы всех сразу.
- **Файл новее — отказ с внятным текстом.** Читать незнакомый формат значит
  на следующей записи превратить содержимое в мусор. Лучше сказать, чем потерять.
- **Битый файл не стирается.** Склад остаётся пустым, но файл лежит на месте —
  вдруг что-то разберётся вручную.

### 4.3 Атомарная запись

Любой файл состояния пишется через временный сосед и переименование
(`writeFileAtomic` в `config.go`). Сбой посередине не оставляет битый файл на
 месте старого.

### 4.4 Пути в настройках

Пути хранятся **относительно папки программы** (`relToExe` / `absToExe`). Причина
прямая: в архиве бэкапа абсолютный путь вида `D:\Users\ivan\...` на другой
машине бессмыслен, а относительный переносится сам.

### 4.5 Смена папки данных

При смене `DataFolder` накопленное **переносится**, а не теряется
(`moveStateFiles`). Переносятся `viewed.json`, `userdata.json` и
`subscriptions.json`; прежние файлы остаются на месте — решать, что старое
место больше не нужно, не дело этой функции. Своё, уже лежащее в новой папке,
чужой копией не затирается.

Подписки после переноса **перечитываются**: они читаются один раз при старте, и
без этого список указывал бы на новую папку, где файла нет, то есть выглядел бы
пустым до следующего перезапуска.

### 5.1 Живая лента (SSE) — главная связь

Раньше окно закачек переспрашивало список каждые три секунды, а отметки
просмотра — каждые десять. Опрос запаздывал (прогресс дёргался раз в три
секунды) и работал вхолостую: между изменениями список приходил тем же самым.

Теперь демон сообщает сам, через `GET /api/events` (`text/event-stream`):

| Событие | Когда | Данные |
| --- | --- | --- |
| `hello` | сразу при подключении | `{}` |
| `torrents` | список раздач изменился | сырой ответ TorrServer |
| `downloads` | прогресс или смена состояния закачки | `{jobs: [...]}` |
| `positions` | изменилась отметка просмотра | хеш, индекс, позиция, длительность |
| `subs` | вышла новая серия по подписке | подписка, номер, найденные раздачи |

Устройство (`events.go`):

- Канал подписчика с буфером на 8. Если интерфейс не успевает читать, из буфера
  вытесняется **самое старое**, и следующее актуальное событие доезжает на его
  место. Отбрасывать новое нельзя: тогда следующее событие тоже не доедет, и
  застрявший интерфейс вечно получал бы устаревшее.
- Событие, которое нельзя превратить в JSON, молча пропускается — рассылка не
  залипает.
- Раз в 25 секунд уходит пустой комментарий `: ping`: соединение через
  промежуточные узлы закрывается по молчанию, а комментарий молчанием не
  считается.
- Обход запросов идёт **только когда есть кому слушать**: без интерфейсов
  сторож в сет�� не ходит вовсе.

Прогресс закачек отсекается порогом в 700 мс. Смена состояния порог
**игнорирует** — «загрузка началась» не должна потеряться из-за экономии одного
события. Но окно порога при этом сдвигается, иначе первый же прогресс после
смены состояния прошёл бы порог и прислал тот же список вторым кадром.

### 5.2 Сторожа

| Сторож | Период | Что делает |
| --- | --- | --- |
| `torrentsWatcher` | 2 с | спрашивает TorrServer `{"action":"list"}`, сравнивает **побайтово** (`bytes.Equal`), при отличии шлёт событие |
| `subsWatcher` | 30 мин | ищет новые серии по подпискам |
| `dl.janitor` | — | убирает завершённые закачки старше суток |
| `viewedJanitor` | — | убирает отметки просмотра старше 90 дней |
| `tmdbSaver` | — | отложенная запись кэша метаданных |

Первая проверка подписок отложена на 90 секунд: демон только что поднялся и сам
ещё занят, и проверка сразу мешала бы первому показу.

### 5.3 Прокси видео

`/ts/` перекладывает поток от TorrServer к браузеру. Отдельная защита не
предусмотрена и не нужна: поток идёт на `127.0.0.1`, недоступный извне.

### 5.4 Защита от браузерных атак

Демон слушает loopback, но `http://127.0.0.1:8099` открыт для **любой** страницы
в браузере пользователя. От этого защищают два фильтра (в `proxy.go`), и оба
работают всегда, независимо от `-host`:

- **`hostGuard`** — сверяет заголовок `Host` со списком ожидаемых. Без этого
  атака DNS-rebinding: злоумышленник поднимает свою страницу на своём домене,
  его DNS указывает на `127.0.0.1`, браузер грузит её с вашего адреса, а адрес
  страницы и адрес, которому браузер доверяет, совпадают.
- **`originGuard`** — для небезопасных методов (POST и прочие) сверяет
  `Origin` и `Sec-Fetch-Site`. Браузер всегда присылает `Origin` при POST, так
  что проверка ловит именно тот случай, ради которого и написана.

Исключения оговорены явно и **только для чтения**: `GET /` и `Sec-Fetch-Site:
cross-site` пропускаются, иначе интерфейс не открылся бы. Небраузерным клиентам
(`curl`, скрипты) ничего не мешает — у них этих заголовков просто нет.

| Кинозал | `/api/kinozal/search`, `/api/kinozal/add` | перебор зеркал, кэш |
| Torznab | `/api/torznab/search`, `/api/torznab/test`, `/api/torznab/sources` | поиск напрямую в индексатор, кэш, ограничитель |
| TMDB | `/api/meta`, `/api/tmdb`, `/api/ratings`, `/api/tv_eps` | кэш метаданных |

Поисковые ручки придерживаются **ограничителем** (`limitSearch`): частые
обращения получают `429`, а не уходят на трекер за капчей.

**Torznab ищется мимо TorrServer** (`torznab.go`). У сервера этот поиск есть,
но он отдаёт только первую страницу, не различает «индексатор не настроен» и
«индексатор упал» и не имеет таймаута — зависший трекер держал бы поиск
открытым. Свой клиент спрашивает все настроенные источники по очереди, сводит
выдачу, убирает совпадения по infohash и отдаёт вместе с разбором по
источникам: пустая выдача с объяснением «у Prowlarr 403» и пустая выдача с
объяснением «все отвечают, ничего не нашлось» — это разные поломки.

Правила стандарта (в `torznabBuildURL`, покрыты тестом) соблюдаются буквально:
`t=search`, `q=`, `cat=`, `limit=100`, `offset=page*limit`, `extended=1`,
`apikey=`. Без `extended=1` индексатор отдаёт почти пустые `item`, и раздач с
размером не видно. Ошибки различаются и называются своими словами: 401/403 —
это ключ, 404 — адрес, таймаут — сеть.

Ключи лежат в `torrclient.json` (`torznab_sources`) и наружу не отдаются: в
ответе `/api/torznab/sources` у источника есть только `has_key` и маска
`key_hint`. Правка адреса без ключа не обнуляет прежний — сервер достраивает
его из старого списка. `torrclient.json` в состав релиза не входит, поэтому
ключ не уезжает в сборку.

**Почему в «ТОП-24» видно не 30.** Число 24 в названии — это часы, а блок
суток на rutor отдаёт 30 раздач (проверено вживую 27.09.2026: ровно 30
`magnet:` до маркера «Самые популярные торренты в категории», в том же числе
и на эталоне `testdata/rutor_top.html`). Резали выдачу не ручки и не
`fetchTop24()`, а фильтры интерфейса, включённые по умолчанию: качество
«1080p и выше» (`isFullHD`) и «только видео». На живой выдаче качество
снимало 5 раздач (`HDTVRip 720p`, `WEBRip 720p`, `WEBRip-AVC`), оставалось 24–25.

Заголовок рисовал число уже отфильтрованных строк, из-за чего
`ТОП-24 за последние 24 часа (24)` читалось как «трекер отдал двадцать
четыре раздачи» — человек искал несуществующее ограничение в трекере. Теперь
заголовок пишет оба числа (`24 из 30`), отсев называется своим фильтром, и
его можно снять кнопкой «показать без фильтра качества» (разовое
`showAnyQual`, сбрасывается новым поиском и сменой настройки качества).
Обрезки до 24 в коде нет ни в одном из двух слоёв.

**Зеркала Кинозала.** Домены живут недолго, поэтому список и есть перебор.
Перебрано 40 доменов вживую (27.09.2026): выдачу отдают только `kinozaltv.life`
и `kinozal.cloudns.nz`. Мёртвые хосты оставлены в списке намеренно, ниже
живых: перебор их переживёт сам, если зеркало оживёт, а начинать с них нельзя —
каждая мёртвая попытка стоит времени ожидания. Свой список зеркал можно задать
в `torrclient.json` (`kinozal_hosts`), он идёт **перед** встроенным. Перебор
вживую: `node tools/check-kinozal.js`.

### 5.6 Подписки на сериалы

Демон сам следит за выходом новых серий, чтобы не спрашивать трекер руками.

- Позиция новизны — последняя известная серия.
- **Первая проверка новизну не объявляет**: только запоминает, что уже вышло.
  Иначе все найденные серии разом пришли бы как «новые», хотя вышли давно.
- Сравнение по границам слов, а не простым поиском подстроки: «Ведьмак 2» —
  другой сериал, и «Дом 2» не должен считать новой раздачу с годом 2019.
- Из выдачи берётся самая поздняя серия; новизна объявляется один раз, событие
  уходит уже **после** сдвига позиции.
- Пауза между запросами к трекеру 2 с, между проверками одной подписки 10 мин,
  расписание раз в 30 мин.
- Разбор названий понимает `S01E02`, `s1.e2`, `1x02`, «3 сезон», «сезон 3-4»,
  «5 серия», «серии 1-10».

### 5.7 Библиотека: фильтры и подборки

Фильтры складываются по И, каждый проверяется один раз на раздачу, а наборы
хешей для избранного и подборок готовятся заранее — иначе поиск по массиву на
каждую раздачу делал бы фильтр квадратичным.

| Фильтр | Поле |
| --- | --- |
| Поиск | подстрока в названии |
| Категория | `movie` / `tv` / `music` / `other` / `uncategorized` |
| Просмотр | `new` / `started` / `done` |
| Подборка | именованный список хешей; отдельно «Избранное» |

Пока включён хоть один фильтр, появляется кнопка сброса и надпись «показано N
из M». Без этого «библиотека пуста» при включённом фильтре выглядела бы как
пропавшие раздачи, а не как отфильтрованная выдача.

Состояние просмотра считается **по видеофайлам**: для сериала «досмотрено» — все
серии, одна начатая делает раздачу начатой. Нет известных файлов (статистика
ещё не подгружена) — раздача считается не начатой, а не пропадает из выдачи.

Подборки, как избранное и закладки, перевозятся между интерфейсом и диском
сквозным складом: демон не разбирает чужие поля, только перевозит.

## 6. Просмотр

- Поток проксируется демоном, адрес для `<video>` есть.
- Позиция хранится по паре «раздача + файл», переживает перезапуск.
- **Продолжение с места остановки** — при возврате окно предлагает продолжить.
- Плеер (VLC/MPC) подключается через HTTP-порт; есть автоопределение доступных.
- Событие `positions` уходит при каждом изменении отметки, файл на диске
  обновляется отложенно (`viewedFlushDue`) — иначе плейлист, который пишет позицию
  раз в несколько секунд, переписывал бы файл непрерывно.

Ограничение честно проговорено: MKV с HEVC и звуком DTS браузер не проиграет.
Обещать обратное нельзя.

## 7. Безопасность и секреты

| Где | Что | Правило |
| --- | --- | --- |
| `torrclient.json` | ключ TMDB, пароли профилей | файл `0600`, в архив бэкапа ключи **не попадают** |
| Бэкап | то же состояние | `tmdb_api_key` и `tmdb_access_token` вырезаются из копии, на диске остаются |
| Файлы состояния | просмотр, избранное, подписки | `0600` |

Бэкап делается по фиксированному списку `backupFiles` — `torrclient.json`,
`userdata.json`, `viewed.json`, `subscriptions.json`; порядок закреплён, чтобы
архив с одним и тем же состоянием выглядел одинаково. Ключи вырезаются не
построчным поиском, а разбором в `map[string]json.RawMessage`: так настройка, о
которой сборка не знает, сохраняется нетронутой, а удаление ключа не задевает
остальное содержимое. Если `torrclient.json` нечитаем, он **пропускается целиком**,
а не переписывается пустым: потерять настройки хуже, чем не положить их в архив.

Архив называется `torrclient-backup-ГГГГММДД-ЧЧММСС.zip`.

Перед восстановлением файлы разбираются — **до** первой записи, иначе битый
архив затёр бы рабочие данные. Проверяются только файлы из `backupFiles`; лишнее
в архиве игнорируется.

### 7.1 Отчёт о состоянии

`GET /api/diagnostics` — кнопка «Собрать отчёт о состоянии» в настройках.
Собирает всё разом то, что иначе пришлось бы собирать по четырём экранам.

| Раздел | Что внутри |
| --- | --- |
| Серверы | каждый профиль: отвечает или нет, версия из `/echo`, таймаут 3 с |
| Папки | watch, загрузки, кэш, данные: доступность, число файлов, размер |
| Файлы состояния | размер и читаемость каждого из `backupFiles` |
| Замечания | всё, что требует внимания, с причиной |

Три решения, которые стоит знать:

- **Секретов в отчёте нет.** Ключ TMDB и пароли не попадают намеренно: отчёт
  предназначен для пересылки, и «пришлите отчёт» не должно уносить с собой пароль
  от раздачи. Это проверяется тестом.
- **Отсутствие файла состояния — не проблема.** На свежей установке их ещё нет, и
  отчёт говорит «ещё не создан», а не «ошибка». Иначе человек начал бы чинить то,
  что не сломано.
- **Совпадение кэша и данных — самое дорогое замечание.** Кэш принято уводить на
  очищаемый диск, и вместе с ним уехали бы подписки и отметки просмотра. Демон
  сравнивает пути сам (`sameFolder`, с учётом регистра букв и хвостового слеша) и
  отмечает это и в отчёте, и плашкой прямо в настройках.

Формат выбирается по `?format=text`. Текст нужен для буфера обмена: разбирать
JSON вручную при отладке неудобно. В браузере отчёт копируется и как файл.

## 8. Проверки

Единая точка входа: **`python tools/check-all.py`** — восемь шагов:

| № | Шаг |
| --- | --- |
| 1 | `gofmt` — демон |
| 2 | `gofmt` — оболочка |
| 3 | `go vet` — демон |
| 4 | `go test` — демон |
| 5 | `node --check` — веб-интерфейс |
| 6 | поведенческие проверки (`check-series.js`) |
| 7 | `go vet` — оболочка |
| 8 | `go test` — оболочка |

Приём гейта необычен и важен: **пустой вывод — успех, любой вывод — провал**,
потому что так ведёт себя `gofmt`, у которого «всё в порядке» это пустой список.
Сеть не требуется, результат воспроизводим.

Отдельно, **вручную** (ходят в сеть, поэтому в гейты не входят):

| Инструмент | Что проверяет |
| --- | --- |
| `node tools/check-kinozal.js` | перебор зеркал Кинозала вживую |
| `node tools/check-series.js` | сериалы, подборки, фильтры, сортировки |
| `python tools/check-storage-live.py` | поведение папок на живом диске |
| `node tools/check-shell.cjs` | оболочка |
| `node tools/check-library-live.cjs` | библиотека вживую |
| `python tools/prove-fix.py` | доказательство исправлений |
| `python tools/make-release.py` | сборка релиза |

Эталонные страницы трекеров лежат в `testdata/` — на них работают разборы и
`fuzz`-проверки, поэтому тесты не зависят от сети.

Покрытие демона: **58 %** операторов. Именно покрытие, а не строки кода,
показывает, где код действительно проверен: раньше `events.go` — то, чем
интерфейс жив, — не был покрыт вовсе.

## 9. Порядок изменений

Изменение считается готовым, когда:

1. проходит `python tools/check-all.py` целиком;
2. добавлена проверка, которая падала бы **до** правки (иначе непонятно, что
   именно исправлено);
3. комментарий объясняет **почему**, а не **что** — по коду видно, что делается,
   но не видно, почему именно так;
4. `gofmt` и `go vet` чисты.

Проверка `-race` требует `gcc` для cgo и в текущей среде не запускается —
это известное ограничение окружения, а не пропущенный шаг.
