## 0. Коротко

Вы правы наполовину. **Архитектура** TorrClientPortable действительно
профессиональнее: один демон + встроенный веб-интерфейс + оболочка Wails,
перебор зеркал, раздельные ошибки по каждому источнику, определение плеера через
реестр, менеджер загрузок, привязка magnet к системе. Hestia до этого не доросла.

Но **поиск** в TorrClientPortable слабее, чем в Hestia, и слабее ровно потому,
что в нём **нет ни одного теста** и нет нормализации разметки. Найдено
**три критических дефекта**, из которых один (страница поиска) делает выдачу
почти бесполезной, а второй (сиды) врёт в интерфейсе на каждой строке.

Самый неприятный вывод: **дефект с сидами виден пользователю как «6 сидов»
превращается в «3 сида / 3 пира»**, а сортировка «по сидам» сортирует по числу
пиров. Это не косметика — по этому числу выбирают раздачу.

### 2.1 Таблица

| | TorrClientPortable | Hestia |

| Перебор зеркал | да (Kinozal, списком хостов) | нет (один живой адрес) |
| Ошибки по источникам | раздельные, собираются на фронте | `emptySearch` различает 3 состояния |

| Адрес трекера | зашит в 3 местах | `search.LiveRutorAddress` + самопочинка конфига |

### 2.2 Где TorrClientPortable действительно сильнее

1. **Разделение демон / интерфейс.** Демон живёт сам, веб-интерфейс можно открыть
   в браузере (`start_web.bat`), Wails — только один из клиентов. У Hestia вся
   логика привязана к окну.
2. **Перебор зеркал.** Список хостов Kinozal и переход на следующий при отказе —
   правильная идея, у Hestia такого нет вовсе.
3. **Ошибки по источникам.** `runSearch` запускает провайдеров параллельно и
   складывает ошибки каждого — пользователь видит, что именно отвалилось.
4. **Функциональная широта:** TMDB-метаданные, рейтинги, список эпизодов,
   менеджер загрузок с прогрессом, watcher папки, привязка magnet-ссылок и
   `.torrent` к системе, «ТОП по категориям».
5. **Один `http.Client` на функцию с внятными таймаутами** — читается проще, чем
   разбросанные по коду `exec.Command`.

### 2.3 Где сильнее Hestia

1. **Тесты.** 499 Go + 34 фронт против нуля. Все три дефекта ниже были бы
   пойманы одним тестом на сохранённой странице.
2. **Нормализация `&nbsp;`.** Hestia заменяет `&nbsp;`/`\u00a0` на пробел **до**
   сопоставления. Без этого регулярка не видит дату и размер: `\s` не считает
   неразрывный пробел пробелом.
3. **Правильный разбор сидов** (см. дефект P0-2) — у Hestia ленивый квантификатор,
   у TorrClientPortable жадный.
4. **Размер по единице измерения**, а не по выравниванию: ячейка комментариев
   стоит в той же колонке и идёт раньше.
5. **Один источник истины для адреса** (`LiveRutorAddress`) и **самопочинка
   конфига**: сохранённое мёртвое зеркало заменяется живым адресом при загрузке.
6. **Проверка TLS** на месте.

## 3. Дефекты поиска: доказательства и исправления

### P0-1. Запрашивается вторая страница выдачи вместо первой

**Код:** `main.go:1627,1631`

```go
items := c.fetchRutorPage("https://rutor.info/search/1/0/000/0/" + url.QueryEscape(q))
```

**Доказательство.** Нумерация страниц у rutor **с нуля**: сама страница
`search/0` в своей пагинации ссылается на `/search/1/...` и `/search/2/...`.
То есть `1` — это **вторая** страница.

Живой замер по запросу `матрица`:

| | `search/0` | `search/1` |
|---|---|---|
| строк | 100 | 100 |
| пересечение id | **0 из 100** | |
| id, первые | 1098254, 1085666, 1084242 | 692183, 661421, 661455 |
| даты, первые | 09 Июл 26, 16 Май 26, 06 Май 26 | 06 Апр 19, 27 Окт 18, 27 Окт 18 |

`search/1` отдаёт раздачи **2018–2019 годов** — у них нет сидов, они мертвы.
Клиент при этом выбрасывает лучшие 100 результатов и показывает следующие 100.
Это и есть «плоховато работает поиск»: пользователь ищет «Матрицу» и получает
раздачи восьмилетней давности.

**Исправление:** `search/0/...` в обоих местах.

```go
const rutorSearchURL = "https://rutor.info/search/0/0/000/0/"

items := c.fetchRutorPage(rutorSearchURL + url.QueryEscape(q))
if len(items) == 0 {
    // rutor периодически отдаёт пустую/капчу-страницу при частых запросах
    time.Sleep(1200 * time.Millisecond)
    items = c.fetchRutorPage(rutorSearchURL + url.QueryEscape(q))
}
```

### P0-2. Сиды читаются как пиры (и показываются неверно)

**Код:** `main.go:1593-1594`

```go
rutorSeedRe = regexp.MustCompile(`<span class="green">(?:.*)([0-9]+)</span>`)
rutorPeerRe = regexp.MustCompile(`<span class="red">(?:.*)([0-9]+)</span>`)
```

**Причина.** `.*` **жадный**: он дотягивается не до закрывающего тега зелёной
ячейки, а до **последнего `</span>` в строке** — а это красная ячейка (пиры).
Обе регулярки возвращают одно и то же число.

**Доказательство.** Реальная строка выдачи (`rutor.info`, раздача 1098254):
сидов **6**, пиров **3**. Прогон регулярок обоих проектов по одной и той же
строке:

| поле | TorrClientPortable | Hestia | истина |
|---|---|---|---|
| сиды | **3** | 6 | 6 |
| пиры | 3 | 3 | 3 |
| размер | 265.94 GB | 265.94 GB | 265.94 GB |
| дата | 09 Июл 26 | 09 Июл 26 | 09 Июл 26 |

Что видит пользователь: в интерфейсе (`app.js:1156-1157`) выводятся
`⬆ seed` и `👥 peer` — то есть **«⬆ 3 👥 3» вместо «⬆ 6 👥 3»**, всегда
одинаковые числа. А сортировка по умолчанию (`app.js:1121`, `onTopClick`)
сортирует по `seed`, то есть фактически **по числу пиров**.

**Исправление:** ленивый квантификатор.

```go
// Ленивый .*? обязателен: жадный .* дотягивается до </span> соседней
// (красной) ячейки и отдаёт число пиров вместо сидов.
rutorSeedRe = regexp.MustCompile(`<span class="green">.*?(-?\d+)\s*</span>`)
rutorPeerRe = regexp.MustCompile(`<span class="red">[^<]*?(-?\d+)\s*</span>`)
```

`[^<]*?` у пиров заодно защищает от того же захвата в обратную сторону.

### P0-3. Источник Kinozal не работает вообще

**Код:** `main.go:1648-1660` (`kinozalHosts`), `fetchKinozal` (1709-1751).

**Доказательство.** Живая проверка всех 11 хостов, запрос
`/browse.php?s=matrix&t=0`:

| хост | ответ |
|---|---|
| `tv.kinozal.app` (первый в списке) | **000** — не отвечает |
| `kinozal.me` | 403 |
| `kinozal.guru` | 403 |
| `kinozal.cloudns.nz` | переход на `/verification?next=…` (защита от ботов) |
| `kinozal.club` | 404 |
| `kinozal.tv`, `.jumpingcrab.com`, `.bz`, `.ist`, `.shop`, `.today` | 000 |

Условие `resp.StatusCode != http.StatusOK || !kzHostOKRe.Match(body)` не
проходит ни на одном хосте → `fetchKinozal` возвращает `nil` → провайдер всегда
пуст. При этом фронтенд (`SEARCH_PROVIDERS = ['rutor','torznab','kinozal','both']`)
честно предлагает его в списке.

**Исправление** (по возрастанию честности):

1. Переставить список: живые хосты вперёд, мёртвые убрать. Сейчас в начале
   стоит тот, что не отвечает.
2. Учитывать защиту от ботов: `cloudns.nz` отдаёт страницу проверки — без
   поддержки cookie её не пройти, хост из списка убрать.
3. Если ни один хост не отдал раздач — **не возвращать `nil` молча**, а отдать
   ошибку вида `kinozal: ни одно зеркало не ответило (проверено N)`, чтобы
   интерфейс показал это рядом с источником, а не «ничего не найдено».
4. Если поддержки не будет — **убрать провайдер из `SEARCH_PROVIDERS`**.
   Мёртвый источник в списке хуже его отсутствия: пользователь считает, что
   «поиск плохой», а на деле не работает конкретный источник.

### P1-4. Берётся 40 строк из 100, пагинации нет

**Код:** `main.go:2006-2008` — `if len(out) > 40 { out = out[:40] }`.

`search/0` отдаёт 100 строк; клиент оставляет 40 и не даёт «следующую страницу».
Нужная раздача может быть на 41-м месте и её не видно.

**Исправление:** либо поднять лимит до 100, либо — правильнее — сделать
пагинацию. Формат адреса известен: `search/<номер>/0/000/0/<запрос>`, номер
начинается с нуля. В API добавить `page`:

```go
func (c *Comp) apiRutorSearch(w http.ResponseWriter, r *http.Request) {
	q := strings.TrimSpace(r.URL.Query().Get("query"))
	page := atoiSafe(r.URL.Query().Get("page")) // 0 по умолчанию
	if page < 0 || page > 20 {
		page = 0
	}
	items := c.rutorSearch(q, page)
	jj(w, map[string]any{"items": items, "page": page})
}
```

и на фронте кнопку «Показать ещё», увеличивающую `page`. Кэш ключевать парой
`(q, page)` — сейчас слот кэша **один** (`rutorSearch.key`), при чередовании
запросов он всегда промахивается.

### P1-5. «ТОП-24» подмешивает категорийные топы

**Код:** `main.go:1965-1967` — `fetchRutorTop()` = `fetchRutorPage("/top/1")`,
и внутри `fetchRutorPage` — та же обрезка по 40.

**Доказательство.** Страница `/top/1` содержит **285 строк** и состоит из
19 блоков:

| блок | строк | даты |
|---|---|---|
| «Топ торренты за последние 24 часа» | **30** | 20 Сен 26, 19 Сен 26 |
| «Самые популярные торренты в категории …» ×18 | 255 | 05 Сен 26, 13 Авг 26, 21 Авг 26, … |

Блок суток — **ровно первые 30 строк**. Обрезка по 40 добавляет **10 строк
категорийных топов**, часть из которых старше месяца. Они попадают в выдачу
«ТОП-24» и там и выглядят как ошибка.

**Исправление:** резать документ по заголовку второго блока, а не по числу
строк. Потребуется разделить `fetchRutorPage` на «получить HTML» и «разобрать
строки»:

```go
// fetchRutorTop читает первый блок /top/1 — «Топ торренты за последние
// 24 часа». Дальше на той же странице начинаются «Самые популярные торренты в
// категории …» — это уже не сутки, и в ТОП-24 попадать не должно.
func (c *Comp) fetchRutorTop() []rutorItem {
	doc := c.fetchPageHTML("https://rutor.info/top/1")
	if doc == "" {
		return nil
	}
	if i := strings.Index(doc, "Самые популярные торренты в категории"); i > 0 {
		doc = doc[:i]
	}
	return parseRutorRows(doc, 40)
}
```

Побочная выгода: перестанет зависеть от того, что у блока суток именно 30 строк.

### P1-6. Ошибки поиска молча превращаются в «ничего не найдено»

**Код:** `main.go:1969-2010`. Любой сбой (`err != nil`, `StatusCode != 200`,
пустой разбор) возвращает `nil`, а `nil` на фронте неотличим от «по запросу
ничего нет».

**Почему это важно.** Три разные ситуации выглядят одинаково:
1. сеть недоступна;
2. rutor отдал капчу/страницу проверки;
3. разметка изменилась и регулярки больше не совпадают.

В третьем случае вы узнаете о поломке от пользователя через месяц. У Hestia для
этого есть `emptySearch`, различающий «поиск не выполнен» / «источник не
ответил» / «ничего не найдено».

**Исправление:** возвращать `([]rutorItem, error)` и различать:
- ошибка сети → `rutor недоступен: <причина>`;
- 200, но ни одной строки → `rutor ответил, но разметка не разобрана (возможна
  капча)`;
- строки есть → нормальный результат.

### P2-7. Отключена проверка TLS

**Код:** `main.go:1713`, `1830`, `1973` — три места с
`TLSClientConfig: &tls.Config{InsecureSkipVerify: true}`.

Проверка сертификата отключена и для rutor, и для Kinozal, и для скачивания
`.torrent`. Для клиента, который в перспективе логинится на трекеры, это
прямая дорога к подмене ответа. Hestia проверяет сертификаты.

**Исправление:** убрать `InsecureSkipVerify` (по умолчанию `false`) и вынести
клиент в общую переменную:

```go
var httpClient = &http.Client{
	Timeout: 15 * time.Second,
	// Проверка сертификата включена. Отключать её ради «чтобы работало» нельзя:
	// через этот же клиент пойдут учётные данные.
}
```

### P2-9. Мёртвый код в `fetchRutorPage`

**Код:** `main.go:1993-1998`

```go
if st := strings.Index(doc, `<div id="index">`); st >= 0 {
	doc = doc[st:]
	if en := strings.Index(doc, `<div id="`); en > 0 {   // <-- никогда не срабатывает
		doc = doc[:en]
	}
}
```

После `doc = doc[st:]` документ **начинается** с `<div id="index">`, поэтому
`strings.Index(doc, '<div id="')` всегда `0`, а условие `en > 0` ложно. Задуманное
«взять только блок выдачи» не происходит — код выглядит как защита, которой нет.

**Исправление:** либо убрать, либо сделать честно — искать закрывающий
`</div>` блока `index`, а не следующий `<div id="`.

## 6. Порядок работ

1. **P0-1** (`search/0`) — одна строка, эффект сразу видно: поиск начинает
   отдавать 2026 год вместо 2018-го.
2. **P0-2** (ленивый квантификатор) — одна строка, в интерфейсе перестают
   дублироваться сиды и пиры.
3. **P0-3** (Kinozal) — решить: починить зеркала или убрать провайдер из списка.
4. **P1-5** (`/top/1`) — резать по заголовку блока.
5. **P1-4** (пагинация) — поднять лимит до 100 как минимум, добавить `page` как
   следующий шаг.
6. **P1-6** (ошибки вместо `nil`) — интерфейс перестанет врать «ничего не
   найдено».
7. **P2-7, P2-9** (TLS, мёртвый код) — гигиена, но TLS стоит закрыть до того,
   как появится вход на трекеры.
8. **P2-8** (тесты) — начать с трёх выше. Без них следующий разбор будет таким
   же: всё проверяется руками на живом сайте.

перепроверить поиск живым запросом: Hestia после этих же правок отдаёт 100
раздач по слову и 100 в режиме 24 часа, все даты внутри суток.
